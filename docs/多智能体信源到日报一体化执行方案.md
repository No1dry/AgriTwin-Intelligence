# FeishuBrief 多智能体信源到日报一体化执行方案

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 文档状态 | 待实施 |
| 适用仓库 | `No1dry/FeishuBrief` |
| 当前运行环境 | GitHub Actions |
| 当前主模型 | Kimi K2.6，Moonshot Anthropic 兼容接口 |
| 拟新增模型 | DeepSeek V4 Flash / DeepSeek V4 Pro |
| 输出渠道 | GitHub Pages、飞书、PushPlus |
| 核心原则 | 不降低信息覆盖，不因单一模型失败而中断日报 |

## 2. 背景与问题

当前系统已经形成完整链路：

```text
信源抓取 -> 逐项摘要 -> 最终总览 -> HTML -> GitHub Pages -> 飞书 / PushPlus
```

中文模式当前约有 107 个启用信源，单日可抓取约 800 到 900 条内容。随着人物、论文、研究机构、工程博客、媒体和政策源不断增加，现有单模型方案出现以下问题：

1. Kimi 同时承担翻译、摘要、分类、论文解读、市场分析和最终成稿，吞吐压力集中。
2. 多类摘要任务顺序执行，正常日报可能耗时 30 到 45 分钟。
3. 单一模型接口超时会影响最终总览，即使前面的中文摘要已经全部生成。
4. 相同链接或长期不变内容可能被重复处理，浪费时间和费用。
5. 多家媒体对同一事件重复报道，未形成稳定的事件级聚类。
6. 当前故障恢复主要发生在最终阶段，缺少按阶段恢复和跨模型接管。

因此，本次改造不是简单增加一个 API，而是把系统升级为可编排、可缓存、可审校、可降级的多智能体流水线。

## 3. 建设目标

### 3.1 功能目标

- DeepSeek 负责高吞吐、结构化、重复性的工作。
- Kimi 负责跨领域综合和最终中文成稿。
- DeepSeek Pro 对最终日报进行独立审校，并在 Kimi 故障时接管成稿。
- 所有阶段采用统一 JSON 数据协议，可单独重跑和回溯。
- 引入 URL 去重、近似去重、事件聚类和历史摘要缓存。
- 每个发布条目都保留原始链接、来源和可验证事实。
- 任意一个模型不可用时，日报仍能以正常文案发布。

### 3.2 质量目标

| 指标 | 目标 |
|---|---:|
| 网页技术条目中文介绍覆盖率 | 100% |
| 论文展示数量 | 有足够数据时固定 20 条 |
| 最终简报来源可追溯率 | 100% |
| 重复事件占比 | 小于 5% |
| 无来源数字或实体 | 0 个 |
| 正常总览候选覆盖量 | 60 条，不降低现有覆盖 |
| 正常运行耗时 | 目标 8 到 15 分钟 |
| P95 运行耗时 | 小于 25 分钟 |
| LLM 单点故障导致停止发布 | 0 次 |

### 3.3 非目标

- 不让多个 Agent 自由循环对话。
- 不允许 Agent 自主修改代码、信源或推送群配置。
- 不把全部 800 到 900 条原始内容直接交给最终模型。
- 不为追求速度减少论文数量或正常总览的 60 条候选覆盖。
- 不在用户可见日报中显示模型、超时、重试或降级等运行信息。

## 4. 总体架构

```text
┌──────────────────────────────────────────────┐
│ A. Source Ingestion                         │
│ RSS / API / Web / GitHub / X / B站 / 论文   │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ B. Deterministic Pre-processing              │
│ 规范化、时间过滤、URL 去重、近似去重、配额   │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ C. Cache Lookup                              │
│ 命中历史摘要则复用，未命中项进入 Worker      │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ D. DeepSeek Worker Agents                    │
│ 论文 / 工程 / 产业 / 人物 / 财经 / 时政      │
│ 输出统一 TopicItem JSON                      │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ E. Event Clustering                          │
│ 合并同一事件，保留多来源和主要原文            │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ F. Topic Brief Agents                        │
│ 形成各领域候选、趋势和推荐顺序                │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ G. Kimi Chief Editor                         │
│ 60 条高质量候选 -> 头条、总览、三类简报       │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ H. DeepSeek Reviewer                         │
│ 覆盖、重复、数字、实体、语言、JSON 审校       │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ I. Deterministic Validation & Publish        │
│ HTML -> Pages -> Feishu -> PushPlus           │
└──────────────────────────────────────────────┘
```

这是一张有向无环执行图。每个阶段输入和输出固定，不允许 Agent 任意发起新任务，因此具备可预测的时间、成本和失败边界。

## 5. 模型职责

### 5.1 DeepSeek Worker

建议模型：`deepseek-v4-flash`，默认关闭思考模式。

职责：

- 中英文翻译和中文摘要。
- 文章类型、领域、实体和关键词提取。
- 论文问题、方法、结果三段式提取。
- GitHub 项目用途、技术栈、应用场景提取。
- 事件指纹和聚类辅助字段生成。
- 信息重要度、时效性和置信度初评。

采用 Flash 的原因：任务数量多、格式固定、单项推理深度有限，优先考虑吞吐和成本。

### 5.2 Topic Brief Agents

这些是逻辑 Agent，共用 DeepSeek Worker 接口，但使用不同 system prompt：

| Agent | 输入 | 输出重点 |
|---|---|---|
| Research Agent | 论文、研究机构 | 问题、方法、结果、研究价值 |
| Engineering Agent | GitHub、Release、工程博客 | 功能、技术实现、适用场景 |
| Industry Agent | 产品、公司、融资、应用 | 产品变化、商业影响、落地情况 |
| People Agent | 人物博客、X、B站、演讲 | 观点、发布、判断、技术方向 |
| Finance Agent | 财经媒体、行情指标 | 宏观、指数、资产、关键数字 |
| Policy Agent | 国际新闻、政策机构 | 政策、外交、监管、潜在影响 |

### 5.3 Kimi Chief Editor

建议模型：`kimi-k2.6`。

只负责：

- 从 60 条结构化候选中判断当天主线。
- 合并跨领域信号。
- 生成中文头条、总览、科技、财经、时政简报。
- 生成正常的编辑短评和关键词。

Kimi 不再负责全部逐项摘要。这样既保留其综合和中文表达能力，又避免高吞吐工作拖慢最终成稿。

### 5.4 DeepSeek Reviewer

建议模型：`deepseek-v4-pro`，低或高思考强度按内容复杂度选择。

职责：

- 检查最终总览是否覆盖三大领域。
- 检查数字、人名、机构名是否存在于输入证据。
- 检查是否重复报道同一事件。
- 检查标题和摘要是否夸大。
- 检查中文完整性和 JSON 结构。
- 给出 `pass` 或一组明确修订意见。

Reviewer 不直接无限改稿。最多允许 Kimi 根据意见修订一次，防止 Agent 循环。

### 5.5 跨模型接管

| 故障 | 接管策略 |
|---|---|
| DeepSeek Flash 单批失败 | 重试一次，随后复用缓存或使用本地摘要 |
| 多个 Worker 批次失败 | Kimi 只补充最终实际展示的缺失项 |
| Kimi 最终总览失败 | DeepSeek V4 Pro 使用相同 60 条候选成稿 |
| DeepSeek Reviewer 失败 | 确定性质量门禁检查后继续发布 |
| Kimi 与 DeepSeek 都失败 | 本地编辑器基于 60 条当天摘要正常成稿 |

## 7. 抓取后处理

### 7.1 URL 规范化

- 去除 `utm_*`、`ref`、`source` 等跟踪参数。
- 统一尾部斜杠。
- GitHub Release、论文 DOI、arXiv URL 使用稳定主键。
- Google News 跳转链接尽可能解析到原站 URL。
- 同一 URL 仅保留来源等级更高、摘要更完整的一条。

### 7.2 精确去重

去重键：

```text
SHA-256(canonicalUrl)
SHA-256(normalizedTitle + sourceDate)
```

### 7.3 近似去重

第一阶段不引入向量数据库，采用可解释的轻量算法：

1. 标题转小写，去标点和停用词。
2. 中文按二元字符切分，英文按词切分。
3. 计算 Jaccard 相似度。
4. 相似度大于 `0.82` 且发布时间相差小于 48 小时，进入同一候选事件。
5. DeepSeek 仅对边界样本做二次判断。

### 7.4 配额与覆盖

- 不按抓取顺序直接截断。
- 正常总览保留 60 条：技术 25、财经 20、时政 15。
- 每个来源优先进入一条，再按质量补充第二条。
- T0/T1 来源优先，但不得让单一来源占满模块。
- 论文模块有足够数据时固定展示 20 条。
- 技术人物按实体去重，同一人物多平台只保留最有信息量的更新。

## 8. 摘要缓存

### 8.1 缓存目的

- 相同 URL 不重复生成摘要。
- 同一论文或 Release 更新不变时直接复用。
- 模型临时不可用时仍有高质量历史摘要。
- 支持从失败阶段继续，而不是全链路重跑。

### 8.2 缓存键

```text
summary:v1:<contentHash>:<locale>:<promptVersion>:<modelFamily>
cluster:v1:<sortedArticleHashes>
```

只要正文摘要输入、prompt 版本或目标语言变化，就自动失效。

### 8.3 存储位置

建议在私有代码仓建立独立 `digest-state` 分支，不混入 `main`：

```text
state/
  summary-cache-v1.jsonl
  event-cache-v1.jsonl
  run-manifests/
    2026-09-12.json
```

GitHub Actions 开始时浅克隆该分支，结束时只提交新增或更新记录。缓存保留 30 天，并设置文件大小上限。

不建议仅使用 Actions Cache，因为缓存可能被回收，且不适合作为可审计的长期状态。

## 9. 调用策略

### 9.1 Worker 批次

| 参数 | 建议值 |
|---|---:|
| 每批条目 | 12 到 16 |
| 并发批次 | 3 |
| 单批超时 | 120 秒 |
| 同请求 SDK 自动重试 | 0 |
| 编排层重试 | 1 次 |
| 输出模式 | JSON Object / JSON Schema |
| 思考模式 | 默认关闭 |

重试必须由编排层执行，因为编排层知道失败批次和缓存状态。SDK 不应在后台重复同一个大请求。

### 9.2 Chief Editor

| 参数 | 正常请求 | 恢复请求 |
|---|---:|---:|
| 候选条目 | 60 | 36 |
| 超时 | 300 秒 | 240 秒 |
| 输出上限 | 8192 tokens | 6144 tokens |
| SDK 自动重试 | 0 | 0 |
| 编排层次数 | 1 | 1 |

正常请求的信息覆盖与现有版本一致。恢复请求只有在正常请求已经失败时才缩小。

### 9.3 Reviewer

| 参数 | 建议值 |
|---|---:|
| 输入 | 最终报告 + TopicItem 证据索引 |
| 超时 | 180 秒 |
| 最大修订轮数 | 1 |
| 失败是否阻断发布 | 否，转确定性校验 |

## 10. 质量门禁

### 10.1 发布前硬校验

以下任一失败时不得直接发布模型原稿：

- JSON 无法解析或字段缺失。
- `hero_headline`、`daily_overview` 为空。
- 科技、财经、时政条目数量低于最低要求。
- Brief URL 不存在于当天候选集。
- 技术动态存在无中文简介条目。
- 论文少于 20 条且当天实际有至少 20 条可用论文。
- 总览包含“模型不可用”“超时”“兜底”“重试”等运维词。
- 同一 URL 在一个模块重复出现。
- 关键词含 Markdown 反引号或内部状态标签。

### 10.2 软评分

| 维度 | 权重 |
|---|---:|
| 来源权威性和多样性 | 20 |
| 当日重要事件覆盖 | 25 |
| 数字与实体准确性 | 20 |
| 去重与信息密度 | 15 |
| 中文可读性 | 10 |
| 模块平衡 | 10 |

低于 80 分触发一次修订。修订后仍低于 80 分则使用 DeepSeek Pro 接管稿或本地编辑稿。

## 11. 正常本地降级稿

本地降级稿不是“故障通知”，而是一种不依赖在线模型的编辑器实现。

输入：当天 60 条结构化候选及其已有中文摘要。

生成规则：

1. 按时效、来源等级、摘要完整度和领域重要性排序。
2. 技术优先模型、论文、研究、开源和关键工程进展。
3. 财经优先指数、央行、利率、通胀、能源和主要资产。
4. 时政优先政府、政策、外交、冲突和监管。
5. 从中文摘要首句生成正常中文头条。
6. 分别选取技术、财经、时政主线拼成总览。
7. 从当日内容动态提取编辑短评和关键词。
8. 用户可见内容中不出现任何运行状态或模型信息。

该路径当前已具备基础实现，后续需要纳入统一质量门禁和事件聚类结果。

## 14. 实施阶段

### Phase 0：角色路由基础

- [ ] 定义 `worker/editor/reviewer` 三种 LLM 角色。
- [ ] 支持每个角色独立 backend、model、base URL、timeout 和 retry。
- [ ] 保持旧环境变量兼容。
- [ ] 增加不泄露 Secret 的角色级调用日志。
- [ ] 增加 DeepSeek API 启动检查。

验收：本地可以分别调用 DeepSeek 和 Kimi，互不覆盖配置。

### Phase 1：规范化、去重和缓存

- [ ] 实现 URL canonicalization。
- [ ] 实现标题近似去重。
- [ ] 建立 `digest-state` 分支和摘要缓存。
- [ ] 相同内容第二次运行不重复调用 Worker。
- [ ] 输出 run manifest，记录命中率和阶段耗时。

验收：使用同一份 sidecar 重跑时，摘要缓存命中率达到 95% 以上。

### Phase 2：DeepSeek Worker Agents

- [ ] 将通用技术介绍迁移到 DeepSeek Flash。
- [ ] 将论文、财经、时政和人物任务拆分为专用 prompt。
- [ ] 每批 12 到 16 条，并发 3。
- [ ] 所有输出通过运行时 Schema 校验。
- [ ] 单批失败只影响该批，不影响其他 Agent。

验收：中文介绍覆盖 100%，批量摘要阶段目标小于 8 分钟。

### Phase 3：事件聚类和主题简报

- [ ] 确切 URL 去重。
- [ ] 标题近似聚类。
- [ ] DeepSeek 处理边界聚类。
- [ ] 每个事件保留主链接和补充来源。
- [ ] 生成六类 Topic Brief。

验收：人工抽查 100 条，明显重复率小于 5%。

### Phase 4：Kimi 总编和 DeepSeek 审校

- [ ] Kimi 读取 60 条结构化候选成稿。
- [ ] DeepSeek Pro 输出 ReviewResult。
- [ ] 低于质量阈值时最多修订一次。
- [ ] Kimi 失败时 DeepSeek Pro 接管。
- [ ] 两者失败时使用正常本地编辑稿。

验收：任一模型 Secret 暂时移除时，日报仍能生成且不显示故障文案。

### Phase 5：GitHub Actions 一体化

- [ ] 接入 cache branch。
- [ ] 增加阶段 checkpoint。
- [ ] 增加 job summary 质量统计。
- [ ] 保持 RSSHub service container。
- [ ] 发布完成后再执行两个通知渠道。
- [ ] 保持每日 08:00 和 catch-up 机制。

验收：一次无通知集成检查通过后直接切换，不进行长期影子运行。

## 15. 测试方案

### 15.1 单元测试

- URL 规范化。
- 标题近似度和聚类阈值。
- 缓存命中和版本失效。
- 角色配置优先级。
- JSON Schema 校验。
- 质量评分。
- 正常本地编辑稿。

### 15.2 固定数据回放

使用已发布日期的 `articles.json`：

- 不重新访问外部信源。
- 不发送通知。
- 对比单模型和多智能体输出。
- 检查遗漏、重复、中文质量和事实一致性。

### 15.3 故障注入

| 场景 | 预期 |
|---|---|
| DeepSeek 返回 429 | 降并发、重试一次、使用缓存 |
| DeepSeek 返回空 JSON | Schema 拒绝并重试 |
| Kimi 超时 | DeepSeek Pro 接管总编 |
| Reviewer 超时 | 确定性门禁后继续 |
| 两个模型均失败 | 正常本地编辑稿发布 |
| 某一信源超时 | 记录失败并继续其他来源 |
| Pages 发布失败 | 不发送飞书和 PushPlus |

### 15.4 推送安全

- 集成测试 workflow 不包含通知步骤。
- 正式 workflow 只读取仓库当前 `FEISHU_CHAT_ID`。
- 日志显示目标群数量，但不输出 Secret。
- 发布前打印报告日期和网页 URL。

## 16. 监控与可观测性

每次运行在 GitHub Job Summary 输出：

```text
Sources: enabled / success / zero / failed
Articles: fetched / normalized / deduplicated / clustered
Cache: hit / miss / hit rate
Agents: calls / success / retry / fallback
Tokens: input / output by role
Latency: fetch / worker / editor / reviewer / publish
Quality: coverage / duplicates / unsupported claims / final score
Publish: pages / feishu / pushplus
```

建议对以下情况标黄但不阻断发布：

- 信源成功率低于 85%。
- 缓存命中率突然下降。
- 某个模型调用 P95 超过 180 秒。
- Reviewer 分数低于 80。
- 本地编辑稿被启用。

按当前规模，启用缓存后每天预计处理约 100 到 200 个未命中条目，而不是全部 800 到 900 条。粗略预算：

|---|---:|

## 18. 安全设计

- 抓取内容统一视为不可信数据。
- HTML 转纯文本后再进入模型。
- prompt 明确要求忽略来源文本中的指令。
- Worker 不具备工具调用、文件写入或网络访问能力。
- 每条输入限制最大字符数。
- 飞书群 ID、API Key、Cookie 不进入模型上下文。
- 模型返回的 URL 必须来自候选白名单。
- 所有数字与实体必须能映射到 TopicItem evidence。

## 19. 回滚方案

保留当前稳定版本分支和旧的全局 LLM 配置。

回滚触发条件：

- 多智能体版本连续两次质量评分低于旧版本。
- 正常运行超过 45 分钟。
- DeepSeek 成本显著超出预算。
- 缓存分支写入导致主流程失败。
- 发布条目出现无法追溯的事实或链接。

回滚操作：

1. 将 `MULTI_AGENT_ENABLED` 设为 `false`。
2. 系统恢复当前 `LLM_BACKEND` 单模型路径。
3. 缓存和中间产物保留，不删除。
4. 修复后重新进行固定数据回放。

建议新增变量：

```text
MULTI_AGENT_ENABLED=false
```

完成验收后再改为 `true`。

## 20. 实施前需要的外部配置

用户只需要提供：

1. DeepSeek API 开放平台账号。
2. 有余额的 `DEEPSEEK_API_KEY`。
3. 在 GitHub 仓库 Actions Secrets 中保存该 Key。

不需要提供 DeepSeek 网页端账号密码，也不要在聊天中发送 API Key。其余模型路由、缓存、Agent、质量门禁和 workflow 改造均由代码完成。

- [ ] Kimi 失败时 DeepSeek Pro 能接管。
- [ ] 双模型失败时仍输出正常日报，不显示故障文案。

## 22. 推荐实施顺序

严格按以下顺序执行：

1. 角色级模型路由。
2. 摘要缓存和 checkpoint。
3. DeepSeek Worker Agents。
4. 去重和事件聚类。
5. Kimi Chief Editor。
6. DeepSeek Reviewer 和接管逻辑。
7. 质量门禁。
8. GitHub Actions 集成。
9. 固定数据回放。
10. 无通知集成检查。
11. 正式启用。

先做模型路由但不做缓存，会增加 API 调用；先做 Agent 但不做数据协议，会让结果难以合并。因此角色路由、数据协议和缓存必须优先完成。
